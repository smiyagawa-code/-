# moc-acs-inventory レビュー（2026-10-05）と修正計画

- 対象：https://moc-acs-inventory.thomas-gra.workers.dev/（公開中の版）
- 方法：Chrome で全タブ・フォルダ・ツールチップ・AI チャットを実際に操作
- 商談日：2026-10-06（明日）

## 1. 機能の理解

ACS 様の 2 課題への対応はこう割り付けられている。

| ACS 様の課題 | モック側の対応 |
|---|---|
| 突き合わせの手作業 | 「フォルダ」の 8月版／9月版 CSV 差分 → 「内示の変更点」カード → 影響部品の表 |
| フォーキャスト読み取りの属人化 | 「計算の決まり」（ルール表 v1 で固定、AI は計算しない）＋ 急ぐ順の集計表 |

AI の役割を「読み取り・注意書き・文面下書き・表への質問」に限定し、**数字は作らない**、という一貫したメッセージ。商談で「AI が勝手に数字を出す不安」を先回りで潰せる構成。

## 2. 気になった点（事実ベース）

| # | 事実 | なぜ問題か |
|---|---|---|
| 1 | 「この案件で遅れの恐れがある部品は？」に対し、AI は「第2工場 外観検査ライン増設：AS-06-148 11日遅れ、手配一覧では AS-04-237・D-1178」と答えたが、その案件の表に AS-06-148 はいない | 「AI は数字を作りません」と謳っている以上、ここを突かれると一番痛い |
| 2 | 組立セル導入を開いた状態で「この案件で」と聞いても 3 案件まとめて返る。おすすめ質問（KS-300、ISE1176）は組立セル（AS-500）に存在しない型番で、フォルダに関係なく固定表示 | チャットが選択中フォルダを見ていない |
| 3 | 「根拠を見る」はメーカー案内（7日遅れ）は出るが、「希望より 15 日遅れ」の内訳（今日＋リードタイム◯日＋案内の遅れ 7 日）が出ない | 計算の決まりを「見せられる」のが売りなら、式に数字が入って見えるべき |
| 4 | 必要数（288/192/192）と在庫＋発注残（228）はあるが、不足＝672−228＝444、ロット切り上げ→460 の中間値が見えない | 「追加手配 460」が飛んで見える |
| 5 | 取消（クリーン仕様 1台→取消）は、増量側の「影響する部品」に相当する「過剰になる部品」が出ず、AI の注意書きの一文だけ | ACS 様の実務では取消による発注残の扱いも痛点のはず（**推測**） |
| 6 | 画面幅を少し狭めるとタブが 2 段に折れる／左サイドバーが長くタブ切替のたびにスクロール位置がずれる／下 3 フォルダの「要確認」の意味が不明／宛先の「ACS の〇〇です」がプレースホルダーのまま | 細かい点 |

## 3. 修正計画（優先度順）

### A. 明日までに直す（デモの信頼性に直結）

| # | 直し方 | 完了の確認 |
|---|---|---|
| A-1（#1） | AI に渡すデータを、表を描いているのと**同じ関数の出力**から作る（別に持っている JSON や文字列を廃止）。案件ごとの部品一覧・遅れ日数・手配数をそのまま渡す | 「この案件で遅れの恐れがある部品は？」の答えに出る型番・日数が、その案件の表と一致する。存在しない型番が出たら不合格 |
| A-2（#2） | チャット送信時に **選択中フォルダ（案件）ID** をコンテキストとして渡し、system 側で「この案件＝◯◯」と明示。他案件は聞かれたときだけ参照 | 組立セル導入を開いて「この案件で」と聞くと組立セルの部品だけ返る |
| A-2'（#2） | おすすめ質問を **フォルダ連動**にする（その案件の部品型番・遅れ・変更点からテンプレで生成） | 組立セルを開くと AS-500 系の型番で質問が並ぶ。中身のない 3 フォルダでは質問を出さない |
| A-3（#3） | 「根拠を見る」に **式と数字** を出す：`希望納期 9/xx` ／ `基準日 9/25 ＋ リードタイム ◯日 ＋ メーカー案内の遅れ 7日 ＝ 入手見込み 10/xx` ／ `差 15日` | 15 日の内訳が足し算で追える |

### B. 時間があれば（提案の説得力が上がる）

| # | 直し方 |
|---|---|
| B-1（#4） | 「不足」列を追加（必要数合計 − 在庫＋発注残）、または「追加手配」セルにホバーで `672 − 228 = 444 → ロット 20 切り上げ 460` の内訳を表示 |
| B-2（#5） | 取消カードにも「過剰になる部品」（発注残のうち不要になる数・金額）を出す。AI の注意書きは「取消分の発注残をメーカーに確認する」文面下書きへ |
| B-3（#6） | タブを `flex-wrap: nowrap` ＋横スクロール、または幅に応じて短縮ラベル／サイドバーを `position: sticky`／「要確認」にツールチップで意味を／宛先プレースホルダーを架空の担当名に |

### C. 商談の進め方（当日までに決める）

| 論点 | 案 |
|---|---|
| デモ導線 | 「内示の変更点 → 影響部品 → 根拠 → 次のアクション」が一番強い。最初に開くタブを「手配を急ぐ部品」のままにするか、「内示の変更点」に変えるか |
| 基準日 | 9/25 固定のまま 10/6 に見せると「期限を過ぎた」が多く並ぶ。①最初に「基準日は 9/25 の想定です」と説明を入れる、②基準日を切り替えられるようにする、のどちらか。①が最小 |

## 4. 作業の順番

1. ソースをこのフォルダに置く（`acs/moc-acs-inventory/`）
2. A-1 → A-2 → A-2' → A-3 の順に直す。各項目で `npm test` を通し、AI の答えを表と照合するテスト（存在しない型番が答えに出ないこと）を `test/` に足す
3. `npm run deploy` → `npm run verify` → ログインして AI の答えを 3 問確認（上の「完了の確認」）
4. C を決め、必要なら最初に開くタブと基準日の説明文を変更して再公開
5. 残り時間で B
